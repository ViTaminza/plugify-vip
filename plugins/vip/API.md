# vip — Plugify API design

The VIP core of the Pisex `cs2-vip` Metamod:Source plugin, ported to a Plugify C++ plugin. This
document is the contract between the plugin (`plugins/vip`) and the VIP modules that used to
talk to it through the `IVIPApi` interface of `ref/src/cs2-vip/include/vip.h`.

Design and file layout follow `plugins/admin_system` (see its API.md): a manifest with plain C
function-pointer methods, headers generated from the manifest with `bin/plugify-gen`, a
hand-written consumer wrapper restoring the Pisex `std::function` interface, an engine-free
static core with its own tests, and a thin s2sdk/pisexcompat glue.

## 2. Boundary rules

1. **Types.** Only `plg::string`, `int32`, `int64`, `bool`, `float`, the three generated enum
   classes and plain C function pointers cross the plugin boundary. No `std::function`, no
   captures, no C++ classes, no exceptions.
2. **`std::string&` out-parameters** do not exist in the VIP interface; the only `ref` parameter
   is `newStatus` of the toggle callback (the original passed `VIP_ToggleState&`).
3. **`SourceMM::PluginId` registration becomes a Register/Unregister pair.** The original keyed
   its listeners by plugin id (one listener per plugin, re-registering replaced it); the pairs
   keep that: registering the same function pointer again replaces nothing, `*_Unregister`
   removes it (idempotent). The consumer wrapper hides this - a module calls
   `VIP_OnVIPLoaded(cb)` / `VIP_OnVIPLoadedUnregister()`.
4. **`const char*` returns become `plg::string`** where the value is short-lived
   (`VIP_GetClientVIPGroup`, `VIP_GetClientFeatureString`, `VIP_GetClientCookie`,
   `VIP_GetTranslate`); the wrapper converts back to the original's `const char*` pointers with
   the original's lifetimes (§5).
5. **`VIP_GetEntitySystem()` is not exported.** The original handed out the `CGameEntitySystem*`
   of the utils API; s2sdk 2.18.2 has no engine layout for it (pisexcompat's
   `GetCGameEntitySystem()` returns nullptr for the same reason), and no pointer can be used
   across the Plugify boundary anyway. `vip::VipApi::VIP_GetEntitySystem()` returns `nullptr`;
   ported modules use the pisexcompat schema helpers / s2sdk entity functions instead.
6. **`VIP_PrintToCenter(int, const char*, ...)` is variadic** and cannot cross the boundary as
   such: the export takes the formatted string and the wrapper does the `vsnprintf` (256 bytes,
   the original's buffer).
7. **No exceptions** escape into the engine: every trampoline of the wrapper and every exported
   function of the plugin catches (`catch (...)` + log).

## 4. Callback values

The generated prototypes are named `...Delegate` on purpose: the wrapper keeps the *original*
`IVIPApi` typedef names (`ItemTogglableCallback`, `ReadyCallbackFunc`, ...) for its
`std::function` types, so a module's source still compiles unchanged; a generated alias with the
same name inside `namespace vip` would collide with it.

| Typedef (Pisex, in the wrapper) | Plugify prototype (generated) | Wrapper (`std::function`) |
| --- | --- | --- |
| `ItemSelectableCallback` | `ItemSelectableDelegate`: `bool(int32 slot, const plg::string& feature)` | `bool(int, const char*)` |
| `ItemTogglableCallback` | `ItemTogglableDelegate`: `bool(int32 slot, const plg::string& feature, ToggleState oldStatus, ToggleState& newStatus)` | `bool(int, const char*, VIP_ToggleState, VIP_ToggleState&)` |
| `ItemDisplayCallback` | `ItemDisplayDelegate`: `plg::string(int32 slot, const plg::string& feature)` | `std::string(int, const char*)` |
| `ReadyCallbackFunc` | `ReadyDelegate`: `void()` | `void()` |
| `ClientLoadedOrDisconnectCallbackFunc` | `ClientLoadedOrDisconnectDelegate`: `void(int32 slot, bool isVIP)` | `void(int, bool)` |
| `SpawnCallbackFunc` | `SpawnDelegate`: `void(int32 slot, int32 team, bool isVIP)` | `void(int, int, bool)` |
| `VIPRemoveCallbackFunc` | `VipRemoveDelegate`: `void(int32 slot, int32 reason)` (`1` = expired, `2` = removed) | `void(int, int)` |
| `VIPAddCallbackFunc` | `VipAddDelegate`: `void(int32 slot)` | `void(int)` |

Feature callbacks are dispatched by the **feature name** the core passes to the trampoline, so
one static trampoline per kind serves every feature a module registered (the original kept one
`std::function` per feature in `g_VipFunctions`).

## 5. Using the API from a module

Include paths and sources (module `CMakeLists.txt`):

```cmake
target_include_directories(my_module SYSTEM PRIVATE
        "${CMAKE_SOURCE_DIR}/plugins/vip/include"                           # vip_api.hpp
        "${CMAKE_SOURCE_DIR}/plugins/vip/include/external/plugify/include"  # generated
        "${CMAKE_SOURCE_DIR}/sdk/include")
target_sources(my_module PRIVATE $<TARGET_OBJECTS:vip_bindings>)
```

Porting recipe:

```cpp
// before (Metamod)
#include "include/vip.h"
IVIPApi* g_pVIPCore;
g_pVIPCore = (IVIPApi*)g_SMAPI->MetaFactory(VIP_INTERFACE, &ret, NULL);
g_pVIPCore->VIP_RegisterFeature("bhop", VIP_BOOL, TOGGLABLE, nullptr, OnToggle);

// after (Plugify)
#include <vip_api.hpp>
vip::IVIPApi* g_pVIPCore = &vip::IVIPApi::Get();   // the class name is an alias of vip::VipApi
g_pVIPCore->VIP_RegisterFeature("bhop", VIP_BOOL, TOGGLABLE, nullptr, OnToggle);
```

Everything else keeps its original spelling: `VIP_IsClientVIP(i)`,
`VIP_GetClientFeatureFloat(i, "speed")`, `VIP_GetClientCookie(i, "bhop")`,
`VIP_OnPlayerSpawn(OnPlayerSpawn)`, the enums `VIP_NULL / VIP_INT / VIP_FLOAT / VIP_BOOL /
VIP_STRING`, `TOGGLABLE / SELECTABLE / HIDE`, `DISABLED / ENABLED / NO_ACCESS`.

The wrapper's enums and types live in `namespace vip` (the Pisex header declared them globally);
a module that keeps the original unqualified spellings adds `using namespace vip;` at the top of
its translation unit - the same convention `plugins/vip_items` and `plugins/vip_smoke` use
(the plugin classes and the generated aliases are then still reachable as `vip::...`).

Lifetime rules of the `const char*` getters (identical to the original's):

* `VIP_GetTranslate` returns a pointer into a per-plugin cache that keeps the value until the
  same key is queried again (the original's `g_vecPhrases` map pointers behaved the same). An
  unknown key answers `""` (the original's `operator[]`), **not** the key itself. The phrase
  table is built at plugin start; there is no phrase reload command (like the original).
* `VIP_GetClientFeatureString` and `VIP_GetClientCookie` return pointers into two separate
  one-value buffers, valid until the next call of the same getter (the original returned a
  `thread_local` buffer for the feature string and the cookie store's pointer for cookies).
* `VIP_GetClientVIPGroup` returns a pointer into a per-slot cache, valid until the group of that
  slot is queried again (the original returned the `std::string` of the player record).
* The `feature` pointer handed to a feature callback points into the wrapper's registration map
  and stays valid until the same feature is registered again.

Callbacks must not throw: the trampolines catch and log through `plg::Log`.

Cookie semantics: `VIP_Get/SetClientCookie(slot, name)` read and write the key
`<group>.<name>` (the group of the player at that moment) in the **official permissions
plugin** - the same keys the original stored through `ICookiesApi`. Without the permissions
plugin the getters answer `""` and the setters fail (the original's `vip_data.ini` fallback is
not ported; the Pisex cookie plugin itself is the `plugins/cookies` port, whose store is
in-memory only).

### When `VIP_OnClientLoaded` fires

The original fired it once per `vip_users` read (connect and `mm_reload_vip`), and - when the
cookies plugin was installed - additionally from its `HookClientCookieLoaded` hook, so a
connected player's cookies were loaded before modules read their toggles. The port keeps both
paths:

1. after the `vip_users` row was read (always), and
2. a second time when the permissions user of that player is loaded **after** that read, so a
   module that reads toggles in its handler sees them. If the user is already loaded when the
   row arrives, no second event is fired.

`VIP_OnClientDisconnect` fires from the s2sdk disconnect listener and from
`VIP_RemoveClientVIP` (with `isVIP = false`), like the original.

## 7. The engine-free core (`vip_core`)

`vip_core` is a static library (plgdb only, no s2sdk, no Plugify types) so the whole
group/database/feature logic is unit-testable and the glue stays thin:

* **Config** — `server_id` of groups.ini (the `sid` column). The group table itself
  (`GroupTable`: group → feature → value) is parsed by the plugin with the pisexcompat KeyValues
  parser (the Pisex `LoadVips()` loop, including the fact that the `server_id` value child
  becomes an empty group that `IsValidGroup` rejects) and handed to `SetGroups()`, which drops
  every per-slot feature cache like `LoadVips()` did. A groups.ini that cannot be read keeps the
  previous table (deviation: the original cleared it first and then failed).
* **Schema** — the `CREATE TABLE vip_users` of `vip.cpp`, byte for byte in the MySQL variant
  (`account_id INT`, `name VARCHAR(64) ... utf8mb4`, `lastvisit INT UNSIGNED`, `sid INT
  UNSIGNED`, `` `group` `` `VARCHAR(64)`, `expires INT UNSIGNED`, `PRIMARY KEY (account_id, sid)`)
  and the same columns for SQLite. Blocking (`QuerySync`), startup only, first failure throws →
  the plugin logs it and fails soft. The table name is shared with the Metamod server on
  purpose: both can run on one database.
* **VIP state** — `IsClientVip`, `AccessTime`, `GroupOf`, `SetAccessTime`, `GiveVip`,
  `RemoveVip`, `SetGroup` reproduce the rules of `VIPApi` including its quirks: a record with
  `TimeEnd == 0` is permanent, `0 < TimeEnd <= now` counts as expired for the API checks (`<=`)
  while the per-second loop expires at `<`, `GiveVip` fails when a record exists (even an
  expired one), `SetGroup` validates the group and the expiry, `GroupOf` does not check the
  expiry at all. `account_id` is the 32 bit account id of the original, not the steamid64.
* **Features** — `ResolveFeatures` is `GetGroupKV()` without the engine checks: the group's
  feature table with the `legacy` chain applied (a child's non-empty value is never overwritten
  by a parent's), cached per slot and invalidated by `SetGroups`, a group change, a disconnect or
  a reload. The `vip::features::Get*` functions are the `VIP_GetClientFeature*` value rules: an
  empty cookie or one whose `atoi()` is non-zero means "enabled", `"0"` (and any unparsable
  value, since `atoi("abc") == 0`) means "switched off" and answers the neutral value
  (`-1`, `false`, `1.0`, `""`); a missing or empty group value answers the same neutral value.
  One deliberate deviation: a `legacy` cycle stops the walk (with an error log) instead of
  hanging the server forever, which is what the original's unbounded loop did.
* **Database work** — `LoadPlayer` (the `SELECT group, expires` of `CheckVIP`/`mm_reload_vip`;
  the record is replaced first, an expired row is DELETEed, the connect path refreshes
  `name`/`lastvisit`, and `onLoaded` reports `{row_found, expired, row_deleted, group, expires}`
  to the plugin), `DeleteExpiredRows` (the `OnStartupServer` cleanup), `DeleteRow`, `InsertRow`
  (the offline `vip_give` branch: the account id is inserted as typed, the name becomes `'none'`).
* **Engine boundary** — the core never asks the engine anything: the plugin passes a
  `VipIdentity` (slot, account id, steamid64, name) and applies what the hooks report back
  (`onLoaded`, `onError`).

Threading: `Query()` never blocks (plgdb worker), all callbacks run on the game thread from
`Poll()`, `CreateSchema()` is the only blocking statement. Results that land after the core was
destroyed are dropped (a lifetime token guards every callback). A load that never answers is
retried by the plugin after 10 seconds (the reconcile).

The tests cover SQLite `:memory:` and MySQL: schema and composite key, give/remove/set access
time/set group, the load paths (missing row, valid row, expired row, reload purpose, other
server), the expiry semantics (`<=` vs `<`, permanent), the startup cleanup, the offline insert,
the feature/cookie value rules, and the `legacy` chain (including the cycle guard).

## 8. The engine side

`src/plugin.cpp` (lifecycle, config/phrase/database loading, s2sdk listeners, the once-per-second
tick, the core hooks, the messages and the 34 exports), `src/commands.cpp` (the commands) and
`src/menus.cpp` (the VIP menu) port `vip.cpp` onto `vip_core` + pisexcompat.
`package.sh` lays out the ready-to-drop package (groups.ini and vip.phrases.txt from
`ref/prod-27016`, the manifest, the `.so` and a `databases.cfg` template).

Commands (same names, same messages as the original; all console-only):

| Name | Behaviour |
| --- | --- |
| `vip_reload` | reloads groups.ini (`LoadVips()`), prints the green "VIP groups has been successfully updated" |
| `mm_reload_vip <userid\|nickname\|accountid>` | re-reads the `vip_users` row of a player; on a valid row prints the Welcome message |
| `vip_remove <userid\|nickname\|accountid>` | `VIP_RemoveClientVIP(slot, notify = true, db = true)` |
| `vip_give <userid\|nickname\|accountid> <time_second> <group>` | gives VIP to an online player (one with a pawn, like the original), or INSERTs the row of a 9–11 digit account id that is offline |

Chat/console: `!menu`-style VIP menu through the `!vip` chat command and the original's
registration `RegCommand({"mm_vip", "sm_vip"}, {"!vip"})`.

Flow: `OnPluginStart` reads `vip.phrases.txt`, the `vip` section of `databases.cfg` (a missing
entry falls back to a local SQLite file), `groups.ini`, creates the schema, registers the s2sdk
listeners (authenticated, put-in-server, disconnect), the permissions `OnUserLoaded` listener,
the commands and the two game events (`player_spawn`, `round_prestart`), and starts the
one-second timer. Authentication (or the once-per-second reconcile over every human slot, which
is the reliable path on a live server) reads the `vip_users` row; the second tick expires VIPs
(fire `VIP_OnVIPClientRemoved(1)`, print `VIPExpired1..3`, DELETE the row) and retries lost
loads.

Deviations of the engine side (all deliberate, the rest is parity):

* `VIP_WarmupPeriod()` reads `CCSGameRules.m_bWarmupPeriod` through `pisex::SchemaOffset`
  (`m_bWarmupPeriod`, `m_bSwitchingTeamsAtRoundReset`, `m_nOvertimePlaying`, `m_bGameRestart`
  for the pistol-round computation are not exposed by s2sdk 2.18.2; the offset lookup returns
  `-1` for an unknown field, so an engine update degrades to the documented default instead of
  reading a wrong address). `m_totalRoundsPlayed` uses the s2sdk accessor.
* The Welcome message of `OnClientPutInServer` uses the tracked/engine player name instead of
  the `name` convar value of the original (same text).
* The welcome/expiry phrases are formatted with `pisex::FormatString` before the chat call, so a
  broken phrase file cannot turn into a format-string bug at the print site (the original passed
  the translation directly as the printf format).
* A missing `databases.cfg`/`vip` section falls back to a local SQLite file instead of failing
  the plugin (the original had no fallback and became a no-op).
* The unported `vip_data.ini` cookie fallback (see §5).
